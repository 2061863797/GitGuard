# GitGuard

GitGuard 是一个 MCP 服务，提供两个工具：

- `check`：检查 `cwd` 仓库里的改动，返回 `PASS` / `WARN` / `REVIEW` / `BLOCK`、`canCommit`，以及带 ID 的 finding。
- `verify`：修复之后，按 finding ID 复验。

每次 `check` 包含三部分：

1. **确定性检查**：密钥扫描默认开启；测试、lint、类型检查只有在仓库的 `.gitguard.yml` 里配置了命令才会执行。
2. **你写的规则**：通过 `rules` 参数传入。
3. **用户写的规则**：仓库 `.gitguard.yml` 的 `rules:`，每次自动带上，你不需要重复。

第 2、3 部分由 TypeSafe System One 判断改动是否违反规则，需要环境变量 `TYPESAFE_API_KEY`。不传规则、yml 里也没有规则时，只跑确定性检查，不需要 Key。

## 什么时候调用

- 完成一个编码任务、准备提交之前，调用 `check`。
- 用户让你检查改动时，调用 `check`。
- 修完 finding 后，用这些 finding 的 ID 调用 `verify`，不要重新从头 `check`。
- **开 PR 之前**，再按整个分支检查一次：`target` 传 `"<基准分支>...HEAD"`，例如 `"main...HEAD"`。单次提交看不出的问题，比如几次提交累积起来的范围蔓延、前后不一致，要在这一步发现。
- `cwd` 必须传仓库的**绝对路径**。
- 范围默认是全部未提交改动（`all`）。只想检查已暂存内容时，传 `scope: "staged"`。
- 把任务描述放进 `task`，System One 会用它理解改动。

## 怎么写规则

每条规则的格式：

```json
{
  "id": "no_float_money",
  "rule": "金额计算不能使用浮点数",
  "level": "block",
  "files": ["src/billing/**"]
}
```

- **直接写规则**，说明代码必须做什么或不能做什么。例如“所有外部输入都必须经过校验”“公开接口必须保持向后兼容”。不要写成问句。
- **规则要具体到能从改动里判断“违反/没违反”**：

  | 好的规则 | 差的规则 |
  |:---|:---|
  | 函数不得超过 50 行 | 代码要写得简洁 |
  | 新增的 HTTP 接口必须校验登录态 | 注意安全 |
  | 金额必须用整数（分）计算，不能用浮点数 | 金额计算要准确 |
  | 修改 `src/api/` 下的公开函数签名时，必须同时更新 `docs/api.md` | 保持文档同步 |

  差的规则没有明确的判断标准，模型只能凭感觉回答，结果不稳定。
- **针对本次任务和这个项目来写**，不要写泛泛的规则。先看 diff、任务要求和项目约定（AGENTS.md、CLAUDE.md、README），再判断最容易出错的地方。
- **一条规则只管一件事**，一般 3~6 条，最多 10 条。
- 可以覆盖这些方向：
  - 任务要求必须全部完成；
  - 不得改动任务范围之外的代码；
  - 行为变化必须有测试；
  - 鉴权、权限、加密、输入校验不得被削弱；
  - 公开接口和数据格式必须兼容；
  - 不得遗留调试代码。
- `id` 只能用小写字母、数字、下划线，不能和 `.gitguard.yml` 里的规则重名。
- `files` 可选：规则只和部分文件有关时加上它，改动没碰到这些文件时会跳过这条规则。
- **`level` 怎么选**：
  - `block`：违反就绝对不能提交，比如泄露数据、破坏核心功能、漏掉任务的核心要求。
  - `review`：需要用户判断，比如改了公开接口、行为变化较大。
  - `warn`：值得一提但不影响提交，比如遗留调试日志。

## 怎么处理结果

返回结果中，`ruleResults` 列出每条规则是否被违反（`violated`）以及理由。`findings` 列出需要处理的问题。

- **`BLOCK`**：修复导致问题的代码，然后用对应的 finding ID 调用 `verify`，直到通过。在这之前不要提交。
- **`REVIEW`**：把 finding 原样告诉用户，由用户决定是否继续。
- **`WARN`**：在回复里简要提一下。
- **`PASS`**：先确认 `diffSummary.filesChanged` 大于 0。如果是 0，说明检查范围是空的，`PASS` 没有意义，要检查 `cwd` 和 `scope`。
- **工具报错**（例如缺少 `TYPESAFE_API_KEY`、配置无效）：把错误原文告诉用户，不要假装检查通过。

## 提交被拦截时

如果仓库里有 `.gitguard.yml`，插件会在 agent 执行 `git commit` 前检查最近一次 GitGuard 检查。出现下面任一情况，提交会被拦截：
- 没有检查记录；
- 要提交的内容和检查时不一致（检查之后又改过文件，或者提交了没检查过的文件）；
- 检查之后 HEAD 变了；
- 最近一次结论是 `BLOCK`。

被拦截时：
- 按拦截提示重新调用 `check`（`scope` 为 `all` 或 `staged`）；
- 如果是 `BLOCK`，先修复，再用 finding ID 调用 `verify`；
- 通过后再提交。

注意，同一条命令里先 `git add` 再 `git commit` 时，所有未提交的改动都必须已经被检查过。

## 禁止事项

- 不能为了通过检查而删规则、放宽规则、降低 `level`。
- 不能修改 `.gitguard.yml`，例如删掉规则或关掉检查命令，除非用户明确要求。
- 不能在 `BLOCK` 未解决时提交，也不能跳过检查直接提交。
- 不能绕过提交拦截，例如改用其他方式写入提交、修改钩子配置或删除 `.git/gitguard/` 下的记录。
